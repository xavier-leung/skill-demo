# 图片逐项验收与三次重做

实际生成时遵循 [依赖图输入规范](image-inputs.md)：工具支持图片输入就传相关参考图，逐张说明位置、尺度与方向约束；不能仅列引用 ID。

存在相邻或内外连通场景时，同时执行 [跨场景空间一致性检查](scene-relations.md)，核对位置、角度、相对大小及连接结构。

同一实体的多状态图同时执行 [分组与冲突检查](asset-groups.md)，每张组内对照图都有独立关键验收项；允许的剧情变化与无依据漂移分别记录。

此规则适用于每一张角色定妆、角色派生、场景、场景俯视图、道具、分镜图。视觉判断由执行技能的模型调用可用看图工具完成；程序只核对记录、版本、重做次数和选优规则，不声称能凭文件字节判断画面含义。

## 固定目标与验收项

首次生成前，从用户描述、已确认设定、镜头要求和参考图拆出 qc.criteria。每项写 id、可观察的 requirement、priority（critical/normal）、weight（正整数）。不要只写“画面好看”或“符合提示词”一个笼统标准，也不要在生成失败后删除难以满足的要求。

至少覆盖本图适用的类别：

- 人物图：身份/脸、年龄感、身形、服装主色和标志细节、要求的视角、人数、肢体完整性。
- 场景图：主要空间布局、门窗/家具位置、识别锚点、光照时段、无人要求。
- 道具图：形状、材质、尺度、开合/破损等剧情状态、背景和无手要求。
- 分镜图：角色与人数、站位左右关系、视线、景别/构图、动作起始状态、服装和道具连续性、画幅。

人物身份、人数、剧情关键物件、必要动作/空间关系通常为 critical；其他细节按影响设权重。至少一项 critical。同一轮所有候选使用同一份标准，不能为了让某张获胜临时调权重。

image.prompt 保存这一张图的目标描述，不随修复改成另一种目标。实际每次提交的提示词放 attempts[].prompt；correction 写本次针对上一张问题做了哪些调整。

建立条目的 qc.criteria 后，获取上下文指纹：

```bash
python3 {skill}/scripts/image_review.py {project} anchors A01 --context
```

将返回值保存到 qc.contextFingerprint。它绑定目标描述、验收项和上游数据/素材。不要在上游改变后仅更新指纹假装旧检查仍有效，要重新看图核对；同一目标的重做计数和历史保留。

## 检查与重做

1. 首张记作 attempt=0，保存独立图片、实际提示词和文件 sha256。
2. **实际打开候选图**，同时查看需要保持一致的参考图。逐项填写 checks：criterionId、result（pass/fail/uncertain）、observation（具体看见了什么）。看不清写 uncertain，不能猜成 pass。调用失败、图片未返回不能伪造看图记录。
3. 所有项 pass 即停止；不用为了“再试试”浪费剩余重做次数。
4. 有 fail/uncertain 时，针对问题修改提示词或参考方式，保持原目标，生成下一张独立文件；依次 attempt=1、2、3。修复一处也要重新检查全部要求，防止修好手却变了脸。
5. 最多重做三次，即首次加重做一共最多四张。不能覆盖旧候选、把同一图片复制多份充当重做，或更换图片 ID、重开会话来重置次数。所有历史保存在本张图的 qc.attempts 中。
6. 每次记录后执行选择脚本。它返回 redo 时继续下一次；返回 selected 时停止生成。重做次数耗尽仍有问题，选最合适的一张，保留并展示未通过项。

```bash
python3 {skill}/scripts/image_review.py {project} anchors A01
# 同样支持 assets Axx、floorplans FPxx、frames Fxx
```

脚本不会代替模型看图，也不会调用生图。先完成真实观察再运行它，不复制示例测试的“通过”记录。

选图后执行正常 workflow submit，展示 HTML 等用户确认。达到三次重做上限不等于用户已经接受残留问题。用户后续明确修改目标或要求追加重做时，先记录这项新指令与旧轮次，不自动循环。

## 选优规则

- 出现全部 pass 的候选：采用首个完全通过的候选，并立即停止。
- 四张都存在问题：先选 critical 未通过项（fail 或 uncertain）数量最少的；再选所有通过项的 weight 总和最高的；再选 uncertain 项最少的；仍相同则采用更早生成的一张，避免默认认为最新版更好。
- `qc.outcome=passed` 表示所有验收项通过。
- `qc.outcome=best_available` 表示重做三次后选优，**仍有不符合或无法判断项**。
- `qc.checked=true` 只表示已完成该轮检查和选图，不等于图片全部合格，更不等于用户确认。

HTML 展示最终选图、结论、采用序号、所有候选和逐项观察；best_available 会明确标注“已重做3次，采用最合适候选；仍有问题”。不能把残留缺陷藏在只有原始 JSON 才看得到的位置。

## 数据要点

图像 qc 在原 checked/notes 之外必须包含：

```json
{
  "contextFingerprint": "由 --context 计算",
  "criteria": [
    {"id":"R01","requirement":"同一人物穿深蓝色外套","priority":"critical","weight":3}
  ],
  "attempts": [
    {
      "attempt":0,
      "file":"images/characters/C01/front-v001.png",
      "sha256":"该文件真实 SHA256",
      "prompt":"本次实际生图提示词",
      "correction":"",
      "checks":[
        {"criterionId":"R01","result":"fail","observation":"外套呈浅灰色，与深蓝色要求不符"}
      ]
    }
  ],
  "selectedAttempt":0,
  "outcome":"pending"
}
```

这只是格式片段，不是可以复制使用的验收结果。准备阶段 checked=false、notes 说明待完成项；每次文件 sha256 使用 core.file_digest 或系统哈希工具获取。正式 file 必须指向选中候选。缺少记录、超次数、旧图改字节、漏验收项、错误选图都会拒绝送审。

生成服务不可用或请求失败时不要无限重试、伪造四张候选或把“未生成”写成视觉不合格；保留已有候选并说明具体阻塞，等工具恢复或用户改变要求。

俯视图必须包含六项固定空间验收标准，见 [场景俯视图](floorplans.md)。它与场景图都使用同一套最多三次重做和候选选优机制。
